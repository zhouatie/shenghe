## Context

价值突变雷达当前使用本地 SQLite 保存观察池、评分、持仓和复盘记录。候选池主要由用户手动录入或 CSV 导入，`refreshQuotes` 只通过 Yahoo Finance 补充个股价格、涨跌幅和成交量。主线雷达由候选池聚合生成，因此板块热度、板块持续性和龙头接力信息仍需要人工维护。

`plate-rotation` skill 已验证可读取两类板块数据：开盘啦源用于观察板块强度和持续性，同花顺源用于观察当日涨幅和爆发。两源的数值量纲不同，不能直接比较或混合计分。

## Goals / Non-Goals

**Goals:**

- 在项目运行时新增原生 TypeScript 板块轮动数据服务，读取板块榜单、排名曲线、龙头矩阵和强度时序。
- 将板块数据落入本地 SQLite，保留数据源、日期、代码、名称、排名、数值和量纲。
- 在主线雷达中展示板块热度、持续性和转折信号，帮助用户识别强势主线。
- 基于板块数据生成市场 60 分建议值和证据说明，用户可采纳或继续人工调整。
- 从板块龙头结果生成候选标的草稿，用户确认后再写入观察池。
- 明确风险提示和数据来源，不输出买卖建议。

**Non-Goals:**

- 不使用板块热度自动生成基本面 40 分。
- 不把 `~/.codex/skills/plate-rotation` 目录作为应用运行时依赖。
- 不引入交易决策、仓位建议、收益预测或价格预测。
- 不做历史行情全量归档，只保存支撑工作台展示和近期研究所需的数据。

## Decisions

### 1. 使用项目内 TypeScript 服务，而不是运行 Python skill 脚本

应用服务端新增 `lib/plate-rotation.ts`，用 `fetch` 直接调用板块接口，并在项目内实现最小必要解析逻辑。

理由：skill 脚本是个人开发工具，不适合作为 Next.js 应用运行时依赖。项目内实现可以统一类型、错误处理、缓存、测试和部署边界。

替代方案：通过 `child_process` 调用 `platerotat.py`。该方案复用快，但会把用户本地 skill 路径、Python 环境和脚本缓存绑定到应用运行时，后续部署和维护成本更高。

### 2. 双源数据分开存储和展示

SQLite 新增板块相关表时必须保存 `source` 和 `value_type`。`kaipan` 的 `score` 只在开盘啦源内部排序，`ths` 的 `pct` 只在同花顺源内部排序。UI 可以并列展示两源，但不能跨源计算“强多少”。

理由：两源反映不同市场语义。开盘啦更偏持续性和强度，同花顺更偏当日涨幅和爆发，混算会制造错误分数。

替代方案：把两源归一化到同一分数。该方案需要额外校准样本，当前没有足够依据，容易误导用户。

### 3. 市场 60 分只生成建议值，不直接覆盖基本面 40 分

板块数据可以映射到 `rs`、`themeScore`、`flow`、`structure` 和 `catalyst` 的建议值，并附带证据来源。保存候选标的时，用户仍可编辑最终评分。`growth`、`position`、`valuation`、`cashflow` 和 `governance` 不由板块轮动数据自动生成。

理由：板块轮动接口描述的是市场热度、资金聚集、排名变化和龙头持续性，不描述公司利润、估值、现金流或治理质量。

替代方案：用板块强度填充全部 100 分。该方案会把短线热度重复计入市场和基本面，导致综合分虚高。

### 4. 候选入池采用草稿确认流

板块龙头结果生成候选草稿，包含名称、代码、主线、标签、市场评分建议和证据。用户点击确认后才调用现有 `upsertCandidate` 写入观察池。

理由：板块龙头是市场信号，不等于用户研究对象。确认流能避免接口结果自动污染观察池。

替代方案：刷新后自动入池 Top 龙头。该方案便利但容易产生大量低质量候选，违背“人工决策”的产品边界。

### 5. 板块刷新与个股行情刷新分离

新增“刷新板块”服务端动作，不复用现有 `refreshQuotes`。现有“刷新行情”继续只负责 Yahoo Finance 个股报价。

理由：两类数据的来源、错误处理、字段语义和刷新频率不同。分离后 UI 状态和错误提示更清晰。

## Risks / Trade-offs

- [上游接口不稳定或返回空数据] → 保存刷新状态和错误消息，UI 明确显示接口空或异常，不用旧数据冒充新数据。
- [HTML in JSON 解析脆弱] → 解析逻辑集中在单一模块，并为典型响应结构补充单元测试夹具。
- [双源量纲被误用] → 类型层保存 `valueType`，展示文案明确标注“强度分”或“涨幅%”，评分建议只使用源内排序和阈值。
- [板块数据刷新变慢] → 服务端设置超时和有限重试，本地缓存近期快照，避免阻塞整个应用状态读取。
- [自动建议影响用户判断] → UI 展示证据和来源，默认仍保留人工编辑入口，并在风险提示中说明所有输出仅供研究复盘。

## Migration Plan

1. 增加 SQLite 表和初始化逻辑，空表不影响旧数据读取。
2. 增加板块数据服务和解析测试，先支持 Top 榜单和排名曲线，再接入龙头与强度时序。
3. 增加服务端动作刷新板块数据，并把刷新摘要并入应用状态。
4. 扩展主线雷达 UI 展示板块数据摘要。
5. 增加候选草稿确认入口，确认后复用现有候选入池逻辑。
6. 更新导出和风险提示。

回滚策略：保留新增表但不读取，移除刷新入口后旧候选池、持仓、复盘和 Yahoo 行情刷新不受影响。

## Open Questions

- 板块接口缓存 TTL 先采用 1 小时，盘中是否需要提供手动强刷新入口由后续实现时确认。
- 评分建议的阈值需要先采用透明规则，后续可根据用户复盘反馈调整。
